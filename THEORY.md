## 1. Machine (Q, 2026-11-24; bandwidths measured by the I-02 probe)

| item | value |
|---|---|
| GPU | 4 × NVIDIA GeForce RTX 5060 Ti, 16660430848 B usable each via `cuDeviceTotalMem` (nvidia-smi shows 16311 MiB) = 66.64 GB ≈ 62.1 GiB total |
| compute capability | sm_120 (GB206) → `-arch=sm_120a` |
| SM count / L2 / clock (Q) | 36 SMs and 32 MiB L2 per GPU; SM clock 2602–2692 MHz idle |
| tensor-core ISA (Q, verified: `ptxas` 13.2 + `cuobjdump -sass`, see `.agents/design/mma-sm120-nvfp4.md`) | `mma.sync.m16n8k16.f32.bf16.bf16.f32` → HMMA **OK**; `mma.sync.m16n8k32.f32.e4m3.e4m3.f32` → FP8 **OK**; `mma.sync.kind::f8f6f4.m16n8k32.f32.e2m1.e2m1.f32` → `QMMA.16832` **OK**; `mma.sync.m16n8k64.kind::mxf4nvf4.block_scale.scale_vec::4X.f32.e2m1.e2m1.f32.ue4m3` → `OMMA.SF.16864.UE4M3.4X` **OK (native NVFP4)**; `tcgen05.mma` **not available on SM120** |

| memory clock (Q) | `cuDeviceGetAttribute` reports **14001 MHz**: 2 × 14.001 GHz × 16 B = **448 GB/s**, which is the spec sheet. nvidia-smi's `clocks.max.memory` 15501 MHz is the boost value and is *not* the basis for the bandwidth |
| memory bandwidth per GPU (Q, measured) | **397.5 GiB/s = 427 GB/s of HBM traffic** (1 GiB device-local copy, read+write, median of 6) = 95 % of the 448 GB/s spec peak → aggregate **1707 GB/s** |
| PCIe (Q, measured) | **one bifurcated Gen4 x16 = 4 × x4**, all four GPUs on the same root complex; P2P enabled by the modified driver. Per GPU **6.73 GiB/s H2D**, **6.66 GiB/s D2H** = 91.7 % of the Gen4 x4 raw 7.34 GiB/s (sysfs `current_link_speed`/`width` read under load). **Aggregate 26.88 GiB/s** (28.9 GB/s) for 4 GPUs on 4 concurrent streams = 92 % of the Gen4 x16 raw 31.5 GB/s. Ordered-pair P2P **6.65–6.66 GiB/s**; 4 KiB round-trip latency **6.0–7.2 µs**; 64 B host↔device round trip **9.4–9.6 µs** |
| CPU | Ryzen 9 5900X, 12C/24T (`getCpuCount` = 24), DDR4 dual-channel; `memcpy` over 2 GiB = **23.5 GiB/s read+write** (25.2 GB/s) |
| system RAM | 60 GB total, ~56 GB available |

**Consequence:** PCIe is a bottleneck for any tier that is not VRAM, and the four
links are separate but share the x16 upstream. Weights that must be read every
token belong in VRAM: streaming one token's 9.92 GB over a single 6.73 GiB/s
link would take 1.5 s, so the 5.81 ms decode step in §2 has to come from HBM.
Comms budget: 1 MiB/token of peer traffic costs 0.15 ms of link time spread over
the four links, and a small (4 KiB) exchange costs 6–7 µs of latency, so a
per-token all-to-all has to be fire-and-forget with one completion wait, not
~100 serialized round trips.
Host RAM is used only for (a) the
51.2 GB n-gram table (gather-only, ~64 KB/token from NVMe/RAM) and (b)
`embed_tokens` (gather-only, 5 KB/token), plus optionally cold experts (lever L5).

## 2. Decode ceiling (memory-bandwidth bound)

Bytes read per emitted token with all weights resident in VRAM:

| variant | bytes/token | ms/token @1707 GB/s | tok/s ceiling |
|---|---:|---:|---:|
| as shipped (bf16 dense, fp4 experts) | 9.92 GB | 5.81 | **172** |
| dense FP8 (L2) | 5.67 GB | 3.32 | **301** |
| + lm_head FP8, experts per-32 scales (L3) | 5.66 GB | 3.32 | 301 |

1707 GB/s is 4 × the measured 427 GB/s per-GPU HBM traffic (`d2d_hbm_gib_s`),
which is the figure for "every weight byte is read once".

Breakdown (as shipped): experts 10/512 × 67.95 = 1.327 · dense 7.26 · lm_head
1.271 · PLE projections 0.065.

**Practical ceiling** = ≈20–40 % of the above (kernel efficiency, 4-GPU latency,
PCIe comms): **35–70 tok/s single-stream** for the as-shipped layout. Any claim
above 172 tok/s is a measurement error.

Speculative decoding (L7) divides the target reads by the accepted length but adds
the draft cost; with an n-gram/prompt-lookup draft (no weights) the realistic
multiplier is 1.4–2.0× at ≥0.6 acceptance.

## 3. Prefill ceiling (compute bound)

Active parameters per token: experts 10/512 × 40.3 B = 0.79 B, dense 3.63 B,
shared expert 0.24 B → **≈4.4 B active** → 8.8 GFLOP/token, plus attention
≈4·L·h·s = 4 × 12 × 2560 × s.

| BF16 tensor peak (M-todo) | ≈95 TFLOPS/GPU (4× FP32 vector) → ~380 TFLOPS aggregate |
| FP8 tensor peak (M-todo) | ≈190 TFLOPS/GPU → ~760 TFLOPS aggregate |
| NVFP4 tensor peak (M-todo) | ≈380 TFLOPS/GPU → **~1500 TFLOPS aggregate** — native `OMMA.SF` block-scaled FP4 *is* available on `sm_120a` |
| practical (30–50 %) | prefill: 450–750 TFLOPS FP4-equivalent aggregate |

**Design consequence (corrected 2026-11-24):** the ModelOpt checkpoint's E4M3
per-16 block scales are *exactly* the operand format of `OMMA.SF` m16n8k64, so
expert prefill GEMM runs as native W4A4 NVFP4 (a labelled quality trade, gated).
A dequantise-to-BF16 + `HMMA` kernel is kept as the exact numerical reference and
fallback. Decode stays a bandwidth-bound dequant-GEMV (FFMA), because M=1 wastes
the tensor core.

At 32 K prompt: ≈13 GFLOP/token ⇒ **20–35 K tok/s** prefill ceiling at 30–50 % of
1500 TFLOPS FP4, realistically **4–10 K tok/s** (bounded by the router/permute
and attention kernels, not the GEMM); short prompts
(≤2 K) are dominated by expert GEMV inefficiency, not FLOPs.

**TTFT floor** = one forward pass of the last prompt token + tokenize + schedule
≈ 10–20 ms once the context is cached.

## 4. State memory — a first-class budget item, not a footnote

Corrected 2026-11-24: an earlier version of this section said 12 KB/token for KV,
which counted K but not V. Real numbers:

| item | per token | per sequence | note |
|---|---:|---:|---|
| KV, 12 full-attn layers (2 kv heads × 256 × K+V × bf16) | **24 KB** | | |
| indexer keys, 12 layers (1 head × 128 × bf16) | 3 KB | | |
| **total full-attention state** | **27 KB/token** | | FP8 halves it to 13.5 KB |
| GDN recurrent state (36 layers × 48 v-heads × 128 × 128 fp32) | — | **113 MB** | *independent of context* |
| GDN conv state (36 × 3 × 10240 bf16) | — | 2.2 MB | |
| PLE conv state + n-gram context | — | ~1 MB | |

### The TP=4 multiplier is the real problem

With TP=4 attention, each rank computes 6 of 24 q heads for **every** sequence, so
every rank needs the whole KV — i.e. **KV is replicated ×4** (this is what vLLM
does too). That multiplies the dominant long-context cost:

| context | KV+idx, 1 copy | ×4 replicated bf16 | ×4 replicated **FP8** |
|---:|---:|---:|---:|
| 4 K | 0.11 GB | 0.45 GB | 0.23 GB |
| 8 K | 0.23 GB | 0.91 GB | 0.45 GB |
| 32 K | 0.91 GB | **3.62 GB** | 1.81 GB |
| 128 K | 3.62 GB | **14.5 GB** | 7.25 GB |

### Envelope implied by the weights budget

Weights after the requant ladder ≈ 65.0 GB of 66.6 GB usable ⇒ **≈1.6 GB of state.**

| workload | state (FP8 KV, ×4) | fits 1.6 GB? |
|---|---:|---|
| 1 × 16 K | 0.79 GB + 113 MB | yes |
| 2 × 8 K | 0.45 + 0.23 | yes |
| 8 × 2 K | 0.20 + 0.90 | yes |
| 8 × 8 K | 0.91 × 2 + 0.90 | no (2.7 GB) |
| 1 × 128 K | 7.25 + 0.11 | **no** |

So the honest statement of this machine's capability for this model is:
**one long context (~16 K) or a handful of short chats — never both at once.**
Three ways to widen it, in order of expected payoff:

1. **KV in FP8** (halves the replicated cost) — standard, small quality cost.
2. **Do not tensor-parallelise the attention layers** — replicate the 1.24 GB of
   attention weights instead and pin each sequence's attention to one rank
   (sequence-parallel attention), broadcasting the result to all ranks for the EP
   MoE step. Costs ~+3.7 GB of weights, saves 3/4 of the KV cost — a win only for
   long contexts, and a net loss at short ones. Decision belongs to I-014.
3. **Free VRAM from weights via the DRAM expert tier** — but this is *not* a
   bottomless source: each 1 GB offloaded costs ~0.15 ms/token at realistic miss
   rates, so ~2–3 GB is the practical maximum before decode latency degrades
   noticeably.

**Resolved by directive:** single-stream, full-context operation means KV is FP8
and stored **once** (attention replicated instead of tensor-parallel); see
`.agents/design/full-context-single-stream.md`. Decode speed is then a curve from
~200 tok/s at short context to ~125-145 tok/s at 256 K.

**Therefore the expert-frequency histogram is the highest-value unmeasured
number in the project**: routing skew decides whether VRAM can hold a much smaller
hot expert set (freeing tens of GB for state) or whether we are stuck near 65 GB.
Measure it as soon as one layer runs (after I-013).

## 5. Quality gates that must hold at every measured point

- Greedy output equivalence against the CPU reference (I-05) on the tiny model:
  bit-identical token ids for 32 tokens.
- Real-model needle-in-haystack at 50 % and ~100 % of the working context.
- Real-model chat + tools round-trip, no degenerate/looping output.
- Any quantization lever (L2, L3) additionally needs: same greedy 64-token
  continuation as the unquantized path on ≥8 fixed prompts, and no increase in
  perplexity proxy beyond the threshold recorded in its issue.
